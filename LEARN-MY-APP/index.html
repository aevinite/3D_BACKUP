Aevidine Restaurant OS — the complete engineering field guide

How your app works, explained from absolute zero

You're a vibe-coder: you build by asking, and you've never been told what the pieces actually are. This guide fixes that — completely. It assumes you know nothing, names every single technology in your project (even the ones you've never heard of), shows you the real folders and real screenshots of your own running site, and explains not just what each thing is but why it's there and how it works together.

By the end you will be able to open your own codebase and know what you're looking at — every folder, every layer, every word people keep saying.

How this guide is built for you. Every idea comes in up to three layers, so you choose your depth:
◆ In kid words the idea with zero jargon.
Normal text the real explanation for your project.
⌗ Technically the precise version — skip it on a first read, come back when curious.
0Start from nothing

Before any code exists

We start below the code — below "frontend," below everything. If you already know this, skim it. If you don't, this is the floor everything else stands on.

What is a computer program?

A computer is powerful but completely stupid: it only ever follows instructions, exactly, one at a time, incredibly fast. A program is just a written list of those instructions. "Code" is the list. "Running" the code means the computer starts at the first instruction and does each one in order until it's done.

In kid words

A program is a recipe. The computer is a chef who can't think for himself — he follows your recipe word for word, at lightning speed, and never guesses. If the food comes out wrong, it's almost always the recipe, not the chef.

What is a programming "language"?

The chef doesn't understand English. You have to write the recipe in a language he was built to read. There are many such languages (each with its own grammar and strengths). Your project's recipes are mostly written in a language called TypeScript — you'll meet it properly in Part 3. For now: a programming language is simply the set of words and grammar you're allowed to write instructions in.

What is the internet, really?

Imagine millions of computers all over the world, connected by cables and radio, able to pass tiny messages to each other in a fraction of a second. That web of connected computers is the internet. Your phone is one of those computers.

Some of those computers have one job: sit switched on, wait for requests, and answer them. We call such a computer a server — because it serves things to whoever asks. A "website" is really just files and answers living on a server somewhere.

Restaurant analogy

A server is a waiter who never sleeps and never leaves. He stands at a window all day. Anyone can walk up and say "bring me the menu," and he fetches it and hands it over. He doesn't care who you are; he just answers requests, one after another, forever.

What happens the moment you tap a link

You're not "opening" a page that already sits on your phone. You're sending a request across the internet: "please send me the page at this address." A server far away receives it, does whatever work is needed (maybe asking a database for today's menu), builds the answer, and sends a copy back to your phone, which then draws it on screen. All of this usually happens in well under a second.

The one sentence to carry through the whole guide

Using a website is two computers having a very fast, very short conversation: yours asks, a server answers. Every term you're about to learn — frontend, backend, database, API, realtime — is just a name for a different part of that one conversation.

1Orientation

What your app actually is

Strip away the code and your project is one clear thing: a restaurant's paper order-pad, printed menu, and kitchen ticket-rail — rebuilt as software that many people share at the same time and that updates instantly for everyone.

When they order, it doesn't just quietly save; it appears within a second on a kitchen screen, a waiter's tablet, and the manager's floor view — exactly like someone shouting "Table 5, one duck!" across a real kitchen. 2Foundations

Frontend, backend, database

These three words get said constantly and defined never. They are the three layers every web app is made of — including yours. Learn them once, here, and 90% of the confusion disappears.

Frontend what people see & tap Backend the rules, run on a server Database where facts are permanently kept

The restaurant version (this analogy runs through the whole guide)

Frontend = the dining room. The menu, the tables, the waiter, everything a guest sees and touches.
Backend = the kitchen. No diner sees it, but it's where the real work and the rules live ("can't cook a dish that's sold out," "staff only past this point").
Database = the walk-in fridge + the ticket spike. The single place holding the true, current state of everything: every dish, every open order, every bill.

The golden rule that ties them together: the frontend never touches the fridge directly. The dining room always sends requests to the kitchen, and the kitchen — enforcing the rules — is the only thing allowed to open the fridge. In software terms: your phone (frontend) never talks straight to the database; it asks the backend, and the backend, after checking the rules, talks to the database. That one discipline is what keeps prices honest and data safe.

Which of your files are which layer

You don't have to guess — you can point at real folders. We'll go deep in Part 5, but here's the map in one breath:

LayerLives inExample from your project
Frontendcomponents/, the page.tsx files, public/panels/FoodCard.tsx draws one dish card; MenuView.tsx draws the whole menu
Backendapp/api/**/route.ts, most of lib/app/api/r/[restaurant]/menu-data/route.ts serves the menu data; lib/tenant.ts figures out which restaurant a URL means
Databasesupabase/migrations/ (its blueprint) — the data itself lives in the cloud001_menu_items.sql created your dishes table; 115 files build the whole schema

Technically

The frontend/backend split in your app isn't only "different folders" — in Next.js it's enforced by where the code runs. Server Components and route.ts handlers execute on the server (they can hold secrets and hit the database with the powerful key). Components marked "use client" ship to and run in the browser (they can never be trusted with secrets). The lib/supabase.ts vs lib/supabaseAdmin.ts split — public key vs service-role key — is exactly this boundary made concrete. You'll see both in Part 8.

3The toolbox

Every technology in your project, named

Your project uses a couple of dozen named tools. Nobody has ever told you what they are — so here is every one of them, grouped by the job it does, with a plain answer and a technical one. When someone says a word ("Tailwind," "Node," "Sentry") you'll know exactly which box it is.

First, the mental model: a "stack"

People call this collection your "stack" — the pile of tools stacked on top of each other to make one app. The bottom of the stack is closest to the raw machine; the top is closest to what the user sees. You don't pick these one-by-one each time; they're chosen together because they work well as a set. Yours is often called "Next.js + Supabase."

Group A — The language layer (what the code is written in)

JavaScript — "java-script"
The one programming language every web browser on Earth can run. If a website does anything interactive — a button reacts, a cart updates — JavaScript is doing it. It is the language of the web; you don't get a choice about it running in browsers.
TypeScript — "type-script" · your main language · files end in .ts / .tsx
JavaScript with a safety layer bolted on. In plain JavaScript you can accidentally do nonsense like add a word to a number and only find out when it breaks in front of a customer. TypeScript makes you label what each value is (a number, some text, a dish), and it catches those mistakes before the code ever runs. Almost every file in your project is TypeScript. This is the "Taiwan lang" you were thinking of — TypeScript.

Technically

TypeScript is a strict superset of JavaScript (every valid JS file is already valid TS). Types are checked at build time and then erased — the browser never sees them; it runs plain JavaScript. The "strict" mode is on in your tsconfig.json, which is why the compiler is picky. The x in .tsx means the file also contains JSX (HTML-like markup mixed into the code — a React thing, below).

Group B — Building the screen (the frontend tools)

React — "re-act" · a library · v19 in your project
A toolbox for building screens out of small reusable pieces called components (a button, a dish card, a cart). Its superpower: when the underlying data changes, React automatically re-draws just the pieces that need updating, so you never hand-rewrite the page. Your FoodCard.tsx, CartPanel.tsx, MenuView.tsx are all React components.

Technically

React keeps a lightweight copy of the UI in memory (the "virtual DOM"), compares it to the previous version whenever state changes ("diffing"), and patches only the real page nodes that differ ("reconciliation"). This is why updating one order tile doesn't repaint the whole 300-table floor. react-dom (a second package you'll see) is the part that actually renders React into a web page specifically.

Next.js — "next jay-ess" · a framework · v16 · the backbone of your app
The big one. React alone only builds screen-pieces; Next.js is the whole house around them — it decides which folder becomes which web address, how a page fetches its data, and where code is allowed to run (server vs browser). Your entire app — all six doors — is a single Next.js app. Part 4 is dedicated to it because it's that central.
Tailwind CSS — "tail-wind" · v4 · how everything is styled
A shortcut for making things look good. Normally you write "styles" (colours, spacing, fonts) in a separate stylesheet. Tailwind lets you instead sprinkle tiny pre-made class names right onto the element — p-4 means "padding size 4," text-lg means "large text." It's faster and keeps the look consistent. This is the "styling language" your app leans on.

Technically

Tailwind is a utility-first CSS framework. At build time it scans your files, sees which utility classes you actually used, and generates only those — so the shipped stylesheet stays tiny. In your project it runs through PostCSS / Lightning CSS (a CSS build tool) via postcss.config.mjs. Related gotcha from your notes: never hand-add the -webkit- prefix for backdrop-filter — this build pipeline adds it for you, and doubling it silently drops the blur.

GSAP — "gee-sap" · animation
An animation engine. It makes things move smoothly — the letter-by-letter reveal of your hero title, the intro splash where the logo scales in from a blur. Used in HeroTitle.tsx and IntroSplash.tsx.
<model-viewer> · the 3D dish viewer
A ready-made web component (a self-contained custom HTML tag) that shows and spins a 3D model. It's what powers the "view in 3D" feature on your dishes. Loaded from a CDN inside PublicModelViewer.tsx.
Recharts · charts & graphs · v3
Draws the graphs in your owner/admin dashboards (sales lines, bars). You give it numbers, it draws the chart. It's built on top of React.
Font Awesome & Google Fonts (Inter, Playfair Display)
Not code you wrote — external design assets loaded in app/layout.tsx. Font Awesome is the icon set (all the little symbols). The two fonts are the typefaces: Playfair Display is the elegant serif for headings, Inter is the clean body font.

Group C — The backend engine & database

Node.js — "node" · the thing that runs your server code
JavaScript was born inside browsers. Node.js is what lets JavaScript run outside a browser — on a server, on your own laptop. When you run npm run dev and your app starts on port 4000, that's Node.js running your Next.js app. So "should I switch to Node.js?" (Part 11) is a slightly confused question — you already use Node.js. It's underneath Next.js right now.

Technically

Node.js is a JavaScript runtime built on Chrome's V8 engine, with extra APIs for file systems, networking, etc. Next.js runs on Node during development and in most production deployments. "Node + Express + a database" is one way to build a backend by hand; Next.js is a higher-level framework that gives you that backend plus the frontend in one, still running on Node.

npm — "n-p-m" · the package manager
The tool that downloads and manages all these other tools. Every dependency above (React, Tailwind, GSAP…) is an "npm package." The package.json file is your shopping list; npm install fetches everything on it into a big node_modules folder. npm run dev starts your app.
Supabase — "soopa-base" · your entire backend-as-a-service
Instead of building and running your own database server, you rent Supabase, which bundles four things you'd otherwise wire up yourself: a database, an auto-built API to reach it, a realtime live-update channel, and file storage. Part 8 breaks all four apart. It's the single most important service your app depends on.
PostgreSQL — "post-gress" · a.k.a. "Postgres" · the actual database inside Supabase
The real, serious, decades-proven database engine that holds every fact in your app — dishes, orders, tables, restaurants, staff. Supabase is the friendly wrapper; Postgres is the engine inside. When people debate "should we use MySQL or Mongo," they're debating whether to swap out this piece (Part 11's answer: don't).

Group D — Shipping, safety & quality (the invisible support crew)

Git · version control · lives in the hidden .git folder
A time machine + save system for code. Every meaningful change is saved as a "commit" you can go back to. It's also how several people (or several of your Claude sessions) work without overwriting each other — each on a "branch," then merged together.
GitHub · where your code lives online
A website that stores your Git history in the cloud so it's backed up and shareable. Your project pushes to a GitHub repository; that's the master copy.
Vercel · what runs your live website
The company that hosts your app on the real internet. When you push code to GitHub, Vercel automatically rebuilds and re-deploys your live site. It's the server-in-the-cloud so you don't run one yourself. (Part 12.)
Sentry · error alarm · v10
A watchtower. If your live app throws an error for a real user, Sentry records it — what broke, where, on what page — so you find out without the user having to report it.
ESLint · the code proofreader
Reads your code and flags likely mistakes and style slips before they cause bugs. npm run lint runs it.
Playwright · the robot tester
Drives a real browser automatically to check things still work — click here, is the price right, did the 3D model re-download. Your scripts/verify-*.mjs files use it. (It's also the tool I just used to screenshot your live pages for this guide.)
esbuild · a fast code bundler
A behind-the-scenes tool that packages JavaScript together quickly. Used by build-vendor.mjs to self-host a copy of the Supabase library for the vanilla-JS panels.
shadcn/ui · a component kit
A collection of ready-made, good-looking building blocks (dialogs, dropdowns, switches) you copy into your project. Your notes say new features should use it. It sits on top of React + Tailwind.

4The backbone

What Next.js really is

Next.js is the single biggest piece of your project, so it gets its own chapter. By the end you'll understand the folder-is-a-URL rule, the difference between a page and an endpoint, and the server-vs-browser split — all with your real files.

Library vs. framework (the distinction that clears up everything)

People sloppily call React and Next.js the same kind of thing. They're not.

  • A library is a box of tools you reach into when you want. React is a library — you call it to build a button. You're in charge; it waits for you.
  • A framework is a pre-built structure that's in charge of the overall shape, and it calls your code at the right moments. Next.js is a framework — it already decided how routing, data-loading, and rendering work; you fill in the blanks it defines.

The house analogy

React hands you a hammer and some excellent tools. Next.js hands you a house that's already built — plumbing run, wiring in, rooms laid out — and says "decorate the rooms." You give up some freedom (the walls are where they are) and in exchange you skip months of laying pipe. For a solo vibe-coder, that trade is almost always worth it.

In kid words

A library is a box of LEGO you build with however you like. A framework is a LEGO set with instructions and a shape already decided — faster to a finished castle, but you follow its plan.

The one rule that explains most of your app/ folder

In Next.js's "App Router" (the modern style your project uses), this rule holds:

A folder is a web address. A special file inside it decides what happens there.

The name and nesting of folders inside app/ literally becomes the URL. What kind of thing lives at that URL depends on which special file you put inside.

Special fileMeansReal example in your app
page.tsx"this folder is a visible screen" — the URL is the folder pathapp/manager/page.tsx → the page at /manager
route.ts"this folder is a backend endpoint" — no screen, just a function that answers requestsapp/api/r/[restaurant]/menu-data/route.ts
layout.tsxa shared frame wrapped around every page beneath itapp/layout.tsx wraps the entire app; app/owner/layout.tsx wraps just the owner pages
[folder] (brackets)a variable slot — any value matches, and gets handed to your codeapp/r/[restaurant]/ matches french-house, demo, any slug
not-found.tsxthe page shown for a bad URL (a 404)app/not-found.tsx

Technically

Straight from the Next.js docs: "a route is only publicly accessible when a page.js or route.js file is present." Any other file you drop in a route folder (a helper, a sub-component) is safely colocated — it lives next to its page without becoming its own URL. That's why your app/item/[slug]/ folder can hold both page.tsx and ItemClient.tsx, and only the page is a real address.

Pages vs. layouts (why your header doesn't flicker)

A page is the content that changes when you navigate. A layout is the frame that stays. Your top-level app/layout.tsx is the frame wrapped around every single screen — it's where the fonts, the theme-picking script, and the always-on guest widgets live. Here's the real, lightly trimmed shape of it:

app/layout.tsx — the frame around your whole app (real, trimmed) export default function RootLayout({ children }) { return ( <html lang="en"> <head> // a tiny script picks light/dark BEFORE the page paints, so it never flashes <script ... /> // warm up + load the fonts and the Font Awesome icons <link href="...Inter + Playfair Display..." /> </head> <body> <RestaurantProvider> {children} // ← the current page is slotted in HERE <GuestChrome /> // ← cart, dining session, toasts — always present on guest pages </RestaurantProvider> </body> </html> ); }

That word children is the key: it's the slot where Next.js drops whichever page you're currently on. Navigate from the menu to a dish, and only children swaps — the <head>, fonts, and widgets around it never rebuild. That's why moving between pages feels instant and the top bar doesn't flash.

The deepest idea: some code runs on the server, some in the browser

This is the concept that trips up every beginner, so slowly:

  • By default in Next.js, a component runs on the server — it renders to finished HTML there, and the browser just receives the result. These can safely touch the database and hold secrets. They're called Server Components.
  • A component that needs to be interactive in the browser (respond to taps, remember a cart, run a timer) must start with the line "use client" at the top of its file. That ships the code to the browser to run there. These can never be trusted with secrets — anything sent to a browser can be read by anyone.

Kitchen vs. dining room, again

Server Components are dishes plated in the kitchen and carried out finished — the guest never sees the cooking. "use client" components are the things that must react at the table: the buzzer that lights up, the little card you flip. The rule "no secrets in client code" is the same as "don't leave the safe combination taped to a dining table."

You can see this split directly in your files. The guest menu page is a Server Component — it looks up the restaurant on the server, then hands off to MenuView.tsx, whose very first line is "use client" because the menu needs to react to taps. Two files, two sides of the fence.

Technically

Server Components ship zero JavaScript for themselves — a real bandwidth win. The boundary is one-directional: a Server Component can render a Client Component, but not vice-versa. Your app/r/[restaurant]/menu/page.tsx is async and awaits the DB on the server (SSR — server-side rendering — so the guest gets complete HTML with no blank flash), then renders the client <MenuView>. This is also why secrets like the service-role key can be read in a route.ts or Server Component but must never be imported into a "use client" file.

Dynamic segments: how one file serves every restaurant

The folder app/r/[restaurant]/ has square brackets, marking restaurant as a variable slot. Whatever real text sits there in the URL gets handed to your code as a value. So one set of files quietly serves every restaurant — french-house, demo, and every future one — by swapping in whichever restaurant's data matches the slug. You never write a new page per restaurant; the bracket does the work. (Part 6 traces exactly how that value becomes a real restaurant.)

Reading a real page, line by line

Theory is over. Let's read an actual file from your project — the guest menu page — and understand every line. This is the file that runs when a guest opens /r/french-house/menu. It's short, and once it clicks, every other page reads the same way.

app/r/[restaurant]/menu/page.tsx — your real guest menu page import { notFound } from "next/navigation"; import MenuView from "@/components/MenuView"; import { getRestaurantBySlug } from "@/lib/tenant"; // White-label: put THIS restaurant's name in the browser tab, not the SaaS brand export async function generateMetadata({ params }) { const { restaurant } = await params; const r = await getRestaurantBySlug(restaurant); return { title: r?.name ? `${r.name} — Menu` : "Menu" }; } export default async function RestaurantMenuPage({ params }) { const { restaurant } = await params; // the slug from the URL, e.g. "french-house" const r = await getRestaurantBySlug(restaurant); // ask the DB: who is that? if (!r || !r.active) notFound(); // unknown/disabled → show 404 return ( <MenuView restaurantId={r.id} restaurantName={r.name} accentColor={r.accentColor} // this restaurant's own colour + branding logoUrl={r.logoUrl} ... /> ); }

What each part is doing

  • The three import lines pull in tools this file needs: a notFound helper, your MenuView component, and the getRestaurantBySlug function. The @/ is a shortcut meaning "from the project root" (set in tsconfig.json) so you don't write long ../../../ paths.
  • generateMetadata runs on the server before the page draws, and sets the browser-tab title to this restaurant's name. That's the "white-label" rule from your CLAUDE.md — a guest at French House never sees "Aevidine" in their tab.
  • RestaurantMenuPage is the page itself. It's async (it can wait for slow things like the database). It reads the slug, looks up the restaurant, and if there's no such active restaurant, shows a 404.
  • The return (…) is JSX — HTML-like markup — handing the restaurant's real data to <MenuView>, which draws the actual menu you saw in Part 1.

That's the entire page. It doesn't draw dishes itself — it figures out which restaurant and delegates the drawing. Notice this file has no "use client", so it's a Server Component: the lookup happens on the server, the guest receives finished HTML.

Following the thread one step deeper: the endpoint that feeds it

Inside MenuView (the client component), instead of every guest's phone hammering the database directly, it fetches from one backend endpoint. Here's that real file — notice how the same getRestaurantBySlug gate reappears:

app/api/r/[restaurant]/menu-data/route.ts — the endpoint MenuView calls export async function GET(_req, ctx) { const { restaurant } = await ctx.params; const r = await getRestaurantBySlug(restaurant); if (!r || !r.active) return NextResponse.json({ error: "not found" }, { status: 404 }); const bundle = await getMenuBundle(r.id); // dishes+categories+settings, CACHED server-side return NextResponse.json(bundle, { headers: { "Cache-Control": "no-store" }, }); }

The comment in your real file explains the why: getMenuBundle caches the heavy database read for ~120 seconds per restaurant, so a hundred guests opening the menu cause one database read, not a hundred. That's your egress-safety discipline (Part 10) baked into a single function. This is exactly the kind of decision you'd never guess from the outside — but now you can read it.

Technically

export async function GET is the Route Handler convention — the function name is the HTTP method it answers. A POST handler in the same file would handle order-placing writes. The ctx.params being a Promise you await is a Next.js 15/16 change (params are async now). Cache-Control: no-store deliberately keeps the browser/CDN from caching, so an owner's menu edit reaches guests via the realtime refetch — the dedup happens in the Next data cache inside getMenuBundle, which is tag-purgeable, rather than an un-purgeable edge cache.

The database, in depth

Every fact your app knows lives in one place: your Supabase database. Every panel is just a different window onto it. This tablet — your waiters' app — is reading the exact same tables the manager and kitchen read, shown for a waiter's job:

Supabase is really four services in one

"Supabase" isn't a single thing — it's four services bundled around one database. Separating them is what makes the whole backend finally click:

Two keys, and why one is dangerous

Every read or write uses one of two keys. Confusing them is the single most dangerous mistake possible in this codebase, so know them cold:

Anon key — the public front-door key (lib/supabase.ts)

Shipped to every guest's browser and openly readable there. Safe only because the database's own rules (RLS, below) limit what it can touch. It opens only the doors marked "public."

Service-role key — the master key (lib/supabaseAdmin.ts)

Lives only on the server, never sent to a browser. Opens every door and bypasses every rule. If it leaks, someone owns your entire database. This is why .env.local is never committed and why I refuse to ever print it in chat.

In kid words

The anon key is like a hotel room key-card: it only opens your room. The service-role key is the manager's master key that opens every room in the hotel. You hand guests a room card; you never tape the master key to the lobby wall.

"Migrations" — your database's own save history

Your supabase/migrations/ folder has 115 numbered .sql files, applied in order, oldest first. Each is one small permanent change to the database's shape. Nobody edits the live database by hand; every change is a new numbered file, so the whole database could be rebuilt from scratch by replaying them. It's the database's version of Git history. In kid words

Think of building with LEGO and taking a photo after every single brick. If you ever knock it over, you can rebuild it perfectly by following the photos in order. The 115 migration files are those photos, for your database.

RLS — the rule that keeps restaurants apart

Every restaurant's rows live in the same tables — one orders table for everyone — each tagged with a restaurant_id. What stops French House from ever seeing Demo's orders is not "the code remembered to filter." It's a rule attached to the table itself, called Row Level Security (RLS), that Postgres enforces on every query no matter what the code asks. Even a bug in your app can't leak across restaurants, because the database itself refuses.

Technically

RLS makes Postgres silently append a WHERE clause to every query on a protected table, from a policy you write once:

create policy "only your own restaurant's orders" on orders for select using (restaurant_id = current_restaurant_id());

After that, every read of orders — from any panel, written by anyone, including a future bug — behaves as if it had WHERE restaurant_id = … attached, whether the code wrote it or not. It's checked per-table and independently on joins. Note: a related gotcha from your CLAUDE.md — new Postgres functions are PUBLIC-executable by default, so every staff-only RPC must REVOKE … FROM anon and GRANT … TO service_role.

RPCs — logic that lives inside the database

An RPC is a function stored in the database and called by name (e.g. "place this order," "close this table," "shift table 5 to table 9"). Putting the logic next to the data means it runs atomically and fast, and the same rule can't be re-implemented three slightly-different ways across three panels. Your app leans on these heavily — the lfh_* functions in your migrations are RPCs.

10Speed & cost

Realtime & the scaling story

The "instant update" that makes your app feel alive is also the thing most likely to cost you money and crash at scale. This chapter is the two real disasters your project already hit and fixed — the best possible teacher, because they actually happened to you.

Here's the kitchen screen — the panel most dependent on instant updates. A ticket must appear the moment a guest orders, move New → Cooking → Ready, and never miss one:

What "realtime" actually is

Normally a screen only knows what it fetched. "Realtime" means the database can push a message to open screens the instant something changes, so they react without you refreshing. Supabase's Realtime service does this over a WebSocket — a connection that stays open both ways, unlike a normal request that closes after one answer.

Analogy

A normal request is mailing a letter and getting one reply. A WebSocket is leaving the phone line open so either side can talk any time. That's how the kitchen "hears" a new order without asking.

War story · 1

The egress crisis (it hit your real quota)

A live panel was re-downloading the entire orders table on every change, for every open tab. When they measured, 96.6% of all data leaving the database was this one wasteful pattern — and it blew past the quota. The fix became a permanent rule: on a live update, fetch only the one table/row that changed (the breadcrumb from Part 7). That cut the traffic by roughly 92%.

The lesson, now law in your project: never re-read the whole board when you know exactly what changed.

War story · 2

The 300-table freeze

The manager floor (the one you saw in Part 1, with its 300 tiles) froze under heavy load. The surprise: it was not a database problem at all — it was the browser. Every update was rebuilding all 300 tiles from scratch. The fix was to patch just the one tile that changed. The database was never the bottleneck; how the frontend repainted was.

The lesson: "slow" isn't always the database — measure which layer is actually slow before "fixing" the wrong one.

Both stories collapse into one rule that now guards every new feature you add: touch only what changed — in the database query, in the live message, and on the screen. This is why your code has that ?table=N targeted refetch and per-tile patching instead of the obvious-but-fatal "just reload everything."

Two more cheap habits already in your app

  • Drop idle connections. A backgrounded phone tab that keeps a live socket open forever is a "phantom user" (you once saw ~41 of them with almost no real traffic). Your panels now drop the realtime channel when a tab is hidden/idle and re-subscribe on return.
  • Pooled connection. Your app uses Supabase's pooled connection, which lets many short requests share a few real database connections — the specific thing that prevents the "too many connections" crash at a busy 300-table peak.

Technically

The pooled connection runs PgBouncer in front of Postgres. The idle-drop is wired via visibilitychange + an idle timer in RealtimeProvider / useRealtime.ts, plus realtime: { worker: true } in lib/supabase.ts so the heartbeat runs in a Web Worker that mobile browsers throttle less (keeping the socket alive across an app-switch). The kitchen/tablet redraw guard uses a boardSig fingerprint that intentionally serialises the full rows minus a small volatile set, so any real field change repaints but heartbeat noise doesn't.

11Straight answer

Should you switch to Node.js + MySQL/MongoDB?

Someone told you "for something big you'll have to switch." You asked me to be brutally honest, so: no — not for the reason implied. Here's the real breakdown, including a correction to the question itself.

First, the correction: you already use Node.js

Node.js is what runs your Next.js app right now (Part 3, Group C). "Switch to Node" isn't a real move — it's already underneath you. What people usually mean is "hand-build your own server with Node + Express + a database, instead of using Next.js + Supabase." That's the comparison below.

CapabilityWhat you have now (Next.js + Supabase)What "roll your own Node + MySQL/Mongo" means
Database enginePostgres — serious, proven, relationalMySQL = a sideways move (same category, no gain). Mongo = a downgrade here (see below).
API serverAuto-generated + your route.ts handlersYou hand-build & maintain an Express server from scratch
RealtimeBuilt in, one line to subscribeYou build your own WebSocket server + reconnection + scaling
File storage (3D, logos)Built in (Storage)You wire up S3 yourself
Tenant isolationEnforced in the database (RLS) — a bug can't leakYou hand-write WHERE restaurant_id=… everywhere & pray nobody forgets one
Hosting / opsManaged — no server to patch or restartYou run, monitor, patch and scale a server yourself

Why MongoDB specifically would hurt you

Your whole app is relationships that must never break: an order belongs to a table, a table to a restaurant, a bill sums specific orders, a dish to a category. A relational database (Postgres/MySQL) is built to guarantee exactly that — it will flat-out refuse to save an order pointing at a table that doesn't exist. MongoDB is designed for the opposite: loose documents with few hard links. Moving to Mongo means giving up guarantees you get free today and re-writing them by hand, worse.

Technically

  • ACID transactions: Postgres makes a multi-step write (order + stock + ticket number) all-or-nothing — what makes your RPCs safe under simultaneous orders.
  • Foreign keys: the DB itself rejects an order pointing at a missing table — Mongo doesn't enforce this natively.
  • Real scale levers are indexing, connection pooling, scoped queries, and pre-aggregated dashboards — none of which need a different engine. You're already doing them (Part 10).

The honest verdict

Stay on Postgres via Supabase. Don't touch the database engine. The problems that actually break "big SaaS" are solved by the discipline you've already been applying, not by swapping frameworks.

Switching now would cost you real months rebuilding capability you already have, for zero new ability to grow. The real trade is control for time — and at your stage, time is far scarcer than control.

Reconsider only if you hit a specific wall Supabase genuinely can't clear (you haven't) — never because "big companies run their own servers." Many big companies also started exactly where you are, on managed infrastructure, and moved only when a concrete limit forced it.

12Going live

How your code becomes a live website

You write code on your Mac. How does it become a site the whole world can open? Four tools hand off in a chain: Git → GitHub → Vercel → your users.

1

Git saves a snapshot on your Mac

You (or I) group changes into a "commit" — a saved snapshot with a note. Git keeps every one, so you can always go back. Work happens on a "branch" (a safe parallel copy) so the live site is never at risk mid-edit.

2

You "push" to GitHub

That sends your commits to GitHub — the cloud master copy. Now it's backed up and shareable. Your project pushes to a private repo.

3

Vercel notices and rebuilds

Vercel watches your GitHub. The moment new code lands on the main branch, it automatically rebuilds the app and deploys it to the real internet — no manual server work.

4

Users open the live site

Within a minute or two, everyone visiting your real URL gets the new version. That's a "deploy."

Analogy

Git is your personal undo-history notebook. GitHub is the shared cloud copy of that notebook. Vercel is the printing press that watches the notebook and re-prints the public newspaper whenever a new page is approved. Users read the newspaper.

The security gate (what's locked and what isn't)

Not every door is open. Your admin room (/aevinite) is password-gated; visiting it without a valid cookie bounces you to this login screen — again, real from your app:

The golden rules of not breaking the live site

  • One task = one branch. Never do unrelated work straight on main; main is what deploys.
  • Secrets never enter the code or chat. They live only in .env.local (on your Mac) and Vercel's settings (for production). If a key ever appears in a message, treat it as compromised.
  • Every database change is additive & safe. Add a column, backfill it, then enforce rules — verify the live menu still works at each step. No big-bang rewrites.
  • Verify before claiming done. Your rulebook demands checking a change in a real browser at desktop and phone width — which is exactly why this guide uses real screenshots instead of promises.

The tool that installs & runs your packages; package.json is its list.
Package / dependency
An external tool your app installs (React, Tailwind…).
Page
A visible screen — a page.tsx file; its folder path is its URL.
Postgres
The relational database engine inside Supabase that holds all your data.
Realtime
Live push updates over a WebSocket, so open screens react the instant data changes.
RLS (Row Level Security)
A rule on a database table the DB enforces on every query — how restaurants stay isolated.
Route Handler
A route.ts backend function; its name (GET/POST) is the request type it answers.
RPC
A function stored inside the database, called by name, run atomically next to the data.
Server Component
A component that runs on the server and ships finished HTML (the default in Next.js). Can hold secrets.
Service-role key / anon key
The unlimited server-only master key vs. the limited public browser key.
Slug
The short URL name of a restaurant (e.g. french-house).
SSR (server-side rendering)
Building the finished HTML on the server before sending it, so the page appears whole, not blank-then-filled.
Stack
The whole set of tools chosen to work together (yours: "Next.js + Supabase").
Supabase
Your backend-as-a-service: Postgres + auto API + realtime + storage.
Tailwind
The utility-class styling tool.
Tenant / multi-tenant
One tenant = one restaurant; multi-tenant = many restaurants sharing one engine, isolated by restaurant_id.
TypeScript
Your main language — JavaScript with a mistake-catching type layer. (The "Taiwan lang.")
Vercel
The service that hosts & auto-deploys your live site from GitHub.
WebSocket
An always-open two-way connection, used for realtime.
White-label
The same app wearing each restaurant's own branding.
