Take-Order Redesign DESIGN REPORT

Waiter tablet · order-taking screen · 2026-07-03 · 3 options with live, scrollable mockups — scroll inside each phone/tablet frame and tap the categories.

What's wrong today

Current behaviour

  • Category chips filter — you see ONE category at a time (or a giant unlabelled "All" wall).
  • Every chip tap re-renders the whole screen — feels like a page swap, not a jump.
  • The dish grid is a small 60vh box with the cart squeezed under it — lots of scrolling inside a scroll.
  • No sense of place: no section headers, no highlight following you as you browse.

What the owner asked for

  • Browse like the guest menu: every category is always there, laid out in one list.
  • Tap a category → instantly shift to that section (scroll jump, not filter).
  • The bar should follow you as you scroll (scroll-spy, Petpooja-style — already built in the guest menu).
  • Keep everything that already works: tap-to-add, options/allergy popup, cart lines, SEND flow.

Option A — "Guest-menu style" phone-perfectsmallest change

One continuous scroll of all categories as sections with sticky section headers. The chip bar pins on top: tapping a chip scrolls to that section; scrolling moves the highlight (scroll-spy). The cart leaves the bottom of the page and becomes a floating gold bar — always visible, tap it to open the order as a bottom sheet with the note/allergy fields and SEND button.

Why it works

  • Exactly the guest-menu mental model the waiter already knows.
  • Zero re-render on category tap — it's just a scroll, so it feels instant.
  • Sticky section headers = you always know where you are.
  • Cart bar keeps count + total in sight without stealing space.

Trade-offs

  • Cart detail is one tap away (bottom sheet) instead of always on screen.
  • On a big tablet, a single column wastes the panel's width.

Option B — "Full POS takeover" fastest for heavy usebigger change

Taking an order takes over the whole screen (today it's crammed into the right half while the floor sits idle on the left). Three panes, like a pro POS (Petpooja/Toast): a category rail on the left (always visible, spy-highlighted), the all-sections dish grid in the middle, and the live cart always on screen on the right with the SEND button. On phones it gracefully collapses into Option A's layout.

Why it works

  • Cart is never hidden — the waiter sees every added line and the total the whole time (fewer mistakes).
  • Vertical rail fits 15+ categories with no horizontal squinting; shows dish counts.
  • Full width = 3–4 dish columns instead of 2 — less scrolling overall.
  • This is what every serious restaurant POS does — waiters who used one feel at home.

Trade-offs

  • More CSS + a new "takeover" mode for the panel (moderate build, ~a day).
  • The live floor is hidden while ordering (fine — "← back" is one tap, and the floor was unusable mid-order anyway).

Option C — "Minimal touch-up" hours, not daysdoesn't really deliver the ask

Keep today's layout exactly, but make the chips jump (scroll to a section in an all-sections list) instead of filtering, and add scroll-spy. No cart bar, no takeover — the cart stays where it is, below the grid.

Why you might pick it

  • Cheapest and safest — a few hours of work, tiny diff.
  • Still kills the worst annoyance (filter + full re-render).

Why I wouldn't

  • The cramped 60vh inner scroll and buried cart remain.
  • On tablet the screen still wastes half its width.
  • We'd likely redo it properly later anyway — double work.

My recommendation A + B MERGED

Build ONE responsive order mode: the screen takes over fully when "＋ Take order" is tapped. Wide screens (tablet) get Option B — rail + all-sections grid + always-visible cart. Narrow screens (phone) get Option A — sticky chips + sections + floating cart bar + bottom-sheet cart. Same HTML, same data, one CSS breakpoint decides which shape you get — exactly how the rest of the panel already adapts at 760px.
  • Everything that works stays: tap-to-add, the options/size/allergy popup, per-line edit, quantities, order note + whole-order allergy, the confirm dialog, SEND — untouched. Only the browsing layout changes.
  • Zero backend / zero egress change: the dishes are already all in memory (state.data.dishes) — we're only changing how they're painted. No new queries, no new realtime.
  • Search stays king: typing collapses the sections into one flat result list (same as today), clearing restores the sections at your old scroll spot.
  • Add-dish-to-existing-order mode gets the same new browser for consistency (it shares the code path today).
  • Back button: the takeover + the cart sheet register with LFH_BACK.layer(…) — hardware back peels the sheet, then the order mode, per the house rule.
