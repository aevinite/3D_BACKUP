2The one big idea: a shared database

This single decision makes everything else cheap and possible. Your instinct (“don’t make a separate database per restaurant”) is exactly right.

We keep one database with the same tables you already have (menu, orders, settings…). We just add one column to each table — restaurant_id — that stamps every row with “which restaurant does this belong to.” Then a security rule makes sure each restaurant can only ever read its own rows.

restaurant_idorder #tabletotalstatus
french-houseKOT‑124₹820cooking
pizza-placeKOT‑39₹540ready
french-houseKOT‑132₹1,240new
cafe-lunaKOT‑71₹260served

🔒 A database‑level filter (Row‑Level Security) guarantees French House cannot see Pizza Place’s rows — even if our app code had a bug.

Why not a separate database each? (Pool vs Silo)

✅ Pool — one DB, rows tagged we use this

  • Cheapest — one database, one set of updates.
  • “All 300 restaurants’ profit on one page” = one quick query.
  • Add a restaurant = add a row, instant.

⚠️ Silo — a separate DB per restaurant

  • 300 databases to update, back up, monitor — ops nightmare.
  • Owner’s one‑page view = querying 300 databases. Painful.
  • Expensive, slow to add restaurants.

Shopify, Slack, Notion, Atlassian all run the “pool” model (shared tables + a tenant id + row‑level security). Separate databases are reserved for huge enterprise/compliance customers only.

The trade‑off, honestlyThe cost of “pool” is discipline.Because everyone shares tables, a careless query could leak data across restaurants. We prevent that by forcing the filter at the database level (not just in app code). That discipline is the price we pay for the low cost and the easy owner dashboard — and it’s the right price.

3Plain‑English glossary

Every scary word you’ve heard, in one or two sentences with an everyday analogy. Read this once and the rest of the page clicks.

Databasethe store of all data
An organised store of your data — tables of rows, like giant linked spreadsheets (a menu table, an orders table…).
PostgreSQL (“Postgres”)our database engine
One of the best free, rock‑solid databases. Great at complex questions, handles JSON, and has built‑in per‑row security. It’s the engine under the hood of your data.
MySQLa different engine
Another popular SQL database — a bit older and simpler. Postgres is more capable for our needs (especially the per‑row security we rely on), which is why we stay on it.
Supabase“Postgres + batteries”
A company that hosts your Postgres database and bundles logins (Auth), file storage (your 3D models & photos), instant APIs, and Realtime — all managed, so you run no servers. You already use it.
Serverless (Vercel)where your app runs
Your app runs as tiny on‑demand copies that Vercel spins up per request and throws away. 300 people scan at once → Vercel runs 300 copies in parallel. There is no single computer whose CPU hits 100%.
Connection poolprotects the database
A database only allows a limited number of live connections. A pooler shares a small set among thousands of requests. Like a receptionist with 5 phone lines handling 500 callers — nobody gets a busy signal.
Indexmakes queries fast
A shortcut the database keeps so it can jump straight to the rows you want. A book’s back‑index vs. reading all 1,000 pages to find “table 42”.
Polling vs Realtimehow screens stay fresh
Polling = asking “anything new?” every second forever (mostly wasted). Realtime = the database taps you on the shoulder only when something actually changes. You already moved off polling — good.
Realtime channelwho gets the nudge
A live “group” for change‑notifications. Like a WhatsApp group per restaurant, not one giant group for the whole city.
Redisa speed cache (later)
A lightning‑fast memory store for answers you reuse a lot. A sticky note for things you’d otherwise recompute constantly. Useful at higher scale — not yet.
Queue / background jobfor slow work (later)
A waiting line for slow tasks (emailing invoices, exports, Zomato sync) so guests never wait for them. Drop the task in a tray; a worker does it in the background.
Read replicafor reports (later)
A read‑only copy of the database. Heavy reports run on the copy so they don’t slow down live ordering on the main one.
Aggregate / summary tablefast dashboards
A small pre‑added‑up table (e.g. “today’s sales per restaurant”) updated as orders arrive. The owner dashboard reads 300 tiny rows, not millions of order rows.

4Why PetPooja breaks at 300 tables — and how we don’t

The “all tables full → errors” crash is almost never the screens. It’s 6 classic backend traps. Here’s each one, and our fix.

Trap A · One overloaded server

✖ The trap

😵 ONE big serverCPU 100% → everything slow

All requests pile onto one machine. At dinner rush it chokes.

✔ Our way

copy
copy
copy
…

Vercel runs as many copies as needed, in parallel. No single CPU to max out.

Trap B · Too many database connections (this is the real “300 tables” crash)

300 app copieseach grabbing a DB line
→
🧑‍💼 Poolershares ~10 real lines
→
🗄️ Databasestays calm

Without the pooler, 300 copies open 300 connections, blow the limit, and you get “too many connections” — the exact peak‑hour error. The pooler (built into Supabase) is the fix.

Our ruleEvery serverless function uses Supabase’s pooled connection, never a direct one. This single setting prevents the most common peak‑load crash.

Trap C · Lazy queries (load a million, use twenty)

✖ The trap

SELECT * FROM orders → load 1,000,000 rows into memory → filter in code → keep 20.

✔ Our way

… WHERE restaurant_id = X AND table = 42 + an index → database returns exactly the 20 you need.

We always filter in the database, scope by restaurant_id, and add an index on every column we filter by. Asking for only what you need is rule #1.

Trap D · Polling every second

✖ Polling

“Anything new?” every 1s × every screen × every restaurant = millions of wasted queries. worst pattern

✔ Realtime push

DB sends one tiny “changed!” nudge only when it changes — then we fetch just that small bit. you already do this

Trap E · One giant realtime channel for everyone

✖ The trap

All 300 restaurants in ONE live group → every kitchen is pinged for every other restaurant’s order. Noise & load explode.

✔ Our way

One channel per restaurant (keyed by restaurant_id). A kitchen hears only its own restaurant.

Trap F · Heavy reports during the dinner rush

Owner opens dashboard“profit, all restaurants”
→
scan millions of rowsduring peak service 😱
orders update a
summary table as they happen
→
dashboard reads
300 tiny rows ⚡

We pre‑add‑up the numbers so the owner’s big dashboard never competes with live ordering. (Read replica added later for even heavier reporting.)

Every serious platform separates live transactions from heavy reporting (often a separate copy/warehouse), uses a connection pooler, indexes everything it filters by, and shards realtime by tenant. None of this is exotic — it’s the standard playbook. We bake the cheap parts in from day one.

Build simple now, but design clean so each upgrade is an addition, not a rewrite. Don’t pre‑build for 300 while you have 7.

Stage 1 · 0–5 restaurantswhere you are / the demo
  • Next.js on Vercel + Supabase as‑is
  • Add restaurant_id + indexes
  • Use the connection pooler
  • Realtime channel per restaurant
  • These are cheap “do‑it‑now” habits
Stage 2 · 5–50growing
  • Summary tables for the owner dashboard
  • Basic monitoring (slow‑query alerts)
  • Bump Supabase tier as needed
  • Cache the rarely‑changing menu
Stage 3 · 50–300+scale
  • Read replica for heavy reports
  • Redis cache for hot reads
  • Queue for slow jobs (invoices, exports, Zomato)
  • Only added when measured — not before
The principle (what good teams live by)“Make it work, make it right, make it fast — in that order.” We add Redis / queues / replicas when a real measurement says we need them, not on a hunch. Over‑building early is itself a way startups die.

6Routing & QR codes — which restaurant am I?

A guest scans a QR at the table. How does the app know which restaurant and table? Here’s my recommendation.

📷 QR on table
→
/r/french-house/t/12slug + table in the link
→
🧭 Resolverslug → restaurant_id
→
🍽️ That restaurant’s
menu · theme · table 12

Start path‑based: the restaurant’s name and table number live right in the QR link. Zero DNS/SSL setup, works today.

The clever bit: one resolver, three address stylesWe build the “which restaurant?” step as a single function. Today it reads the path (/r/french-house). Later, the very same function can also recognise a subdomain (frenchhouse.app.com) or a restaurant’s own domain (frenchhouse.com) — that becomes a config flip per restaurant, not a rewrite. This is exactly how Vercel & Shopify do it.
Trade‑offPath‑based feels a little less “their own brand” than a custom domain. But it’s free, instant, and we keep the upgrade path open — so premium restaurants can get their own domain later as a paid perk.

7Feature switches & white‑label look

This is where your “turn off ratings for just one restaurant” lives — and why it isn’t working today.

Two switches in a row (this clears up admin vs owner)

🛰️ Admin allows it?your SaaS plan/tier
→
👑 Owner turns it on?their choice
→
💡 Guest sees the featureonly if BOTH say yes

Admin decides what a restaurant is allowed to have; the owner decides what’s switched on. The guest sees it only when both agree.

Why your toggle “doesn’t work” today (my read of the code)The wiring is mostly correct — every feature does check its switch. The two real problems: (1) the guest’s browser remembers the old switches and keeps showing them until a reload; and (2) there are two different toggle screens (your Manager panel’s “Features” tab and the Admin panel) both writing the same place, so it feels random. I’ll confirm this live before fixing.
The fixMake switches per‑restaurant, refresh the guest the instant a switch changes (no stale memory), and keep one toggle screen as the source of truth.

White‑label: themeable, not hand‑built per restaurant

Each restaurant stores its brand colour, logo, font, name, hero image as data on its row. The guest app paints itself from those. A “template” choice can handle bigger layout differences later.

Trade‑offA themeable single app gives genuinely distinct‑looking restaurants cheaply and at scale. Fully hand‑built separate frontends per restaurant is an agency model — expensive and doesn’t scale to 300 — so we keep that for special cases only.

9The build order — and how we stay safe

Six steps in dependency order. Each becomes its own small plan. Step 0 is the keystone everything else needs.

Tenancy core · the keystone

Add the restaurants table + restaurant_id everywhere, per‑restaurant settings & ticket counters, the “which restaurant?” resolver, and safely move your current live restaurant in as “restaurant #1”.

Guest tenant resolution

QR/slug → the correct restaurant’s menu, settings & theme. needs 0

Per‑restaurant features + white‑label

Move switches per‑restaurant, fix the stale‑memory toggle bug, merge the two toggle screens, add theming. needs 0,1

Roles & permissions

Add the Owner role, manager‑power switches, re‑lock the panels for public hosting. needs 0

Owner panel (5th panel)

Manage staff, set manager powers, toggle features, and the all‑restaurants profit view. needs 3

Admin super‑panel

Owners tab, search restaurants, set each restaurant’s allowed features (entitlements). needs 0,3

Biggest risk — said plainlyThis is a live restaurant. A multi‑tenant change touches every table. So we do every database change additively: add the column defaulting to “restaurant #1”, fill it in, then switch on enforcement — and we check the live menu still works at each step. Never a big‑bang rewrite. Phase 0 especially is one careful branch.
