### What pass 4 corrected — again all in the checks, and two of them mattered

Run against `main` after the fixes and the four leftovers were merged and deployed.

1. **The suite could delete another terminal's order. Fixed.** `mine.orders` was filled from
   `lfh_active_orders`, and on a SHARED table that list legitimately contains the other diners'
   orders — that is what a shared bill *is*. So "everything I can see" was being treated as "mine to
   remove". Both runners now snapshot the tracked ids **before** placing and claim only the id that
   *appears* after their own tap. Checked afterwards: every row the cleanup had touched carried this
   terminal's own test signature and fell inside its own run windows, so nothing of another
   session's was lost — but the design was one busy table away from doing exactly that.
2. **The suite pre-checked shared state and then asserted on it.** Blocks 3b and 5 picked a table
   with no open session, then asserted the gate would say "your table isn't open yet". A session
   appeared at that table *between* the check and the tap (ten terminals share this restaurant, and
   French House also carries sessions left open for days), so the row went red on a race of its own
   making. Both now **branch on the screen the app actually shows** and drive all three legitimate
   states to the same end — an order in the kitchen:
   `isn't open yet` → ask staff, staff open it, the gate carries on by itself ·
   `what should we call you` → the table is open and empty, become its head here ·
   `already open` → someone else's party, back out without touching it.
3. **The gate CLOSING is a correct outcome, not a crash.** After a request to staff, the watcher can
   carry the guest in the instant the table opens — so the sheet finishes the job and disappears.
   Reading `.sg-title` unconditionally timed out on a gate that had simply succeeded, which is the
   very thing P01355 exists to prove.

### Worth knowing about the dev stack (not a product fault)

French House's test tables carry a lot of debris from many sweeps — table 25 alone has ~90 CLOSED
sessions, and tables 20 and 29 have sessions still marked `open` from 2026-08-06 and 2026-08-17.
That is why any assumption about a table's state keeps breaking. Deliberately **not** cleared here:
closing sessions in bulk is a "delete whatever is there" filter over other sessions' work, which is
exactly what this ledger's own rules forbid.


### Pass 5 — what it settled, and the one thing it did not

Run against the merged, deployed `main`. **Blocks 1+2, 3a (52), 3b (31) and 4 green in the combined
run**; block 5's 25 rows green when run on their own. So every one of the 500 has passed on this
build — but not all five blocks in a single sitting.

**Block 5 is the problem, and it is the HARNESS.** It failed three times in three different ways,
each time for an environmental reason and never for a product reason:

1. the app's own per-table guest limits, tripped by the cumulative load of running five blocks in
   six minutes (the thing CLAUDE.md forbids). Fixed: `run-all.mjs` now waits out the limit window —
   75 s before the end-to-end block, 165 s before block 5, which joins twice and orders.
2. a table it had pre-checked as free acquiring a session before the tap. Fixed: the INSERT is now
   the check (`idx_one_open_session_per_table` means the database refuses a second open session, so
   trying is atomic where asking-then-trying is a race).
3. its own move-the-party test relocating its own session mid-run, after which later rows compared
   against the table number they had started with. Fixed: only assert the move when the update was
   actually accepted, and pick a destination the database will take.

**WHAT I GOT WRONG ABOUT THIS, and corrected the same day.** I wrote block 5's contention up as
"needs a decision about the shared test stack" and listed it for the owner. That was wrong, and he
said so: *"I still didn't understand what you need permission for."* Nothing here was his to decide.
Block 5 is a test script in this repo; making it survive a fixture it shares with ten other terminals
is the script's job, not a product choice, and there was no trade-off for him to weigh either way.
Escalating it put work back on him that was mine.

**How it is actually solved.** The whole attempt is now retryable (`runAttempt()` in
`scripts/sweep/t3/across-panels.mjs`): up to three goes, each cleaning up everything it made by id,
waiting 90 s for the restaurant's own limit window to roll over, and rotating to a different table so
a retry cannot walk back into the same contention. A REAL fault fails all three attempts; contention
passes on a later one. No dedicated restaurant, no cross-terminal convention, nothing for anyone to
approve.
