## How they run

```sh
npm run verify:t28-new50 -- --base http://localhost:4428
```

Two halves, deliberately. The **pure** half calls the SHIPPED exported functions — compiled with
esbuild at run time, never re-typed, because a check that re-implements the logic only proves the
re-implementation — and reads the real answer. The **driven** half posts to a running dev server as
a real owner, as the admin, and with no cookies at all, and reads the rendered answer: the status,
the body, and the database row a write left behind. Every row it writes is deleted by its own id in
the same run. Nothing answering at the base prints "nothing was checked" and exits 2, never a stack
trace that reads like the app is broken.

The ids are **auto-numbered in declaration order** from the block's first id, and the run refuses to
start unless there are exactly fifty. Typed ids are how a generated band ends up with two of the
same number — this registry records six such collisions.

**Judged by breaking it, not by the green.** Four shipped behaviours were reverted one at a time —
the item-name fallback, the finite-number test on an outlet id, the no-secret refusal in the webhook
lock, and `ownerActorName`'s name-before-uuid order — and the matching rows went red every time
(P104301, P104302, P104310, P104311, P104331). Restoring them turned the suite green again.
